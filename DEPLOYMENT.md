# Deployment

Target topology:

```text
Browser
  │  https://<your-app>.vercel.app          (static SPA from apps/web)
  │     /api/*  ──rewrite──▶ https://<api>.onrender.com/api/*   (first-party cookies)
  │  wss://<api>.onrender.com/socket.io       (Socket.IO, JWT in handshake)
  ▼
Render Web Service  ludo-nova-api   (apps/server, Node 24, 1 instance)
  ├── Render PostgreSQL   ludo-nova-db   (DATABASE_URL)
  └── Render Key Value    ludo-nova-kv   (REDIS_URL, Redis-compatible)
```

Secrets (`DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, `JWT_REFRESH_SECRET`) exist **only**
on Render. Vercel only ever sees public `VITE_*` values.

---

## 1. Render (API + PostgreSQL + Key Value)

The repository contains a free-tier Blueprint: [`render.yaml`](render.yaml).

1. Push the repository to GitHub.
2. Render dashboard → **New → Blueprint** → pick the repository. Render creates:
   * `ludo-nova-api` — free web service (Node runtime)
     * build: `npm ci --include=dev && npm run build:server`
     * start: `npm run db:deploy && node apps/server/dist/index.js` (free services do not support a separate pre-deploy command)
     * health check: `GET /health` → `{"status":"ok"}`
     * auto-deploy only after GitHub checks pass (`autoDeployTrigger: checksPass`)
   * `ludo-nova-db` — free PostgreSQL (`DATABASE_URL` wired automatically)
   * `ludo-nova-kv` — free Key Value / Redis (`REDIS_URL` wired automatically)
   * `JWT_SECRET` / `JWT_REFRESH_SECRET` — generated by Render
3. When prompted for `CLIENT_URL`, enter your planned Vercel production origin, e.g.
   `https://ludo-nova.vercel.app`. After deploying the frontend, set this to the exact
   production origin (and any custom domain), comma-separated, with no trailing slash.
4. Confirm the Blueprint preview shows **Free** for all three services before
   confirming. Deploy, then check `https://<api>.onrender.com/health` and `/health/ready`
   (the latter also pings PostgreSQL and Redis).

Free-tier limitations: the API sleeps after 15 minutes without traffic and can take
about a minute to wake. Free PostgreSQL storage is limited and the database expires
after 30 days; export any data you need before then. Free Key Value data is not
persistent across restarts. These limits make this suitable for a demo or hobby test,
not reliable production use.

### Environment variables (server)

| Variable | Required | Notes |
| --- | --- | --- |
| `NODE_ENV` | yes | `production` |
| `PORT` | auto | Render injects it |
| `DATABASE_URL` | yes | from the Render database |
| `REDIS_URL` | recommended | from Render Key Value. Without it, in-memory equivalents are used |
| `JWT_SECRET` | yes | ≥ 32 chars, generated |
| `JWT_REFRESH_SECRET` | yes | ≥ 32 chars, different from `JWT_SECRET` |
| `CLIENT_URL` | yes | allowed browser origins (CORS + CSRF origin check) |
| `COOKIE_SAMESITE` | no | `lax` with the Vercel rewrite (default). `none` only for direct cross-site API calls |
| `TRUST_PROXY` | no | `1` on Render |
| `DISCONNECT_GRACE_SECONDS` | no | seat hold time after a disconnect (default 120) |
| `LOG_LEVEL` | no | `info` |

The server refuses to start in production with test-only settings
(`DICE_SEED`, `TEST_TURN_SECONDS`, `RATE_LIMIT_DISABLED`) or identical JWT secrets.

### Instance sizing

Game sessions live in the memory of the instance that created them, so run **one**
instance and scale vertically.

**Measured** with `tests/load/socket-load.mjs` on a development laptop (one Node 24
process running via `tsx`, local PostgreSQL, no Redis):

| Scenario | Result |
| --- | --- |
| 400 sockets, 100 concurrent 4-player games | 371 persisted actions/s, ack p50 90 ms / p95 143 ms, 0 errors |
| 400 sockets, 50 concurrent 8-player games | 343 persisted actions/s, ack p50 36 ms / p95 55 ms, 0 errors |
| Reconnect storm (400 sockets at once) | 400/400 sessions restored, p95 1.5 s |
| 300 rapid / invalid requests from one socket | rate-limited, then the socket is disconnected; server healthy |

Human play generates roughly 0.5–1 action per second per game, so the measured
throughput leaves wide headroom. **Estimated** starting points (not measured on Render):

| Render plan | Suggested ceiling |
| --- | --- |
| Starter (0.5 CPU / 512 MB) | ~300 concurrent players / ~75 games |
| Standard (1 CPU / 2 GB) | ~1,000 players / ~250 games |
| Pro (2 CPU / 4 GB) | ~2,000+ players / ~500 games |

Validate on your own plan by running the load script against a staging service.

Each game action costs one PostgreSQL transaction (events + snapshot). The free
database is suitable only for testing: it has limited storage and expires
after 30 days. For ongoing traffic, use a database plan with persistent storage.
Horizontal scaling needs sticky game ownership (see "Known limitations" in the README).

## 2. Vercel (web)

1. Vercel Hobby is the no-cost choice for personal, non-commercial projects.
   Vercel → **Add New → Project** → import the repository.
2. **Root Directory:** `apps/web` (keep "Include files outside the root directory" enabled).
   [`apps/web/vercel.json`](apps/web/vercel.json) sets install (`npm ci` at the repo root),
   build (`npm run build`), output (`dist`), SPA fallback, caching and security headers.
3. **Edit the API rewrite** in `apps/web/vercel.json`:
   ```json
   { "source": "/api/:path*", "destination": "https://<your-api>.onrender.com/api/:path*" }
   ```
   The rewrite makes `/api` same-origin, so the httpOnly refresh cookie is a
   first-party cookie (works in Safari and with third-party cookies blocked).
4. Environment variables (Production + Preview):

   | Variable | Value |
   | --- | --- |
   | `VITE_API_URL` | `/api` |
   | `VITE_SOCKET_URL` | `https://<your-api>.onrender.com` |
   | `VITE_SITE_URL` | `https://<your-app>.vercel.app` (canonical/OG/sitemap) |

   Never add `DATABASE_URL`, `JWT_SECRET` or `REDIS_URL` to Vercel.
5. Deploy, then add the exact Vercel production origin to `CLIENT_URL` on Render
   and redeploy the API if Render does not redeploy automatically.

`npm run build` generates `robots.txt` (disallows `/game/`, `/room/`, `/solo/game`,
`/profile`, `/settings`, `/api/`) and `sitemap.xml` from `VITE_SITE_URL`.

### PWA on Vercel

The build emits `sw.js`, `workbox-*.js`, `manifest.webmanifest` and `icons/*` at the
site root. `apps/web/vercel.json` already:

* excludes them (and `robots.txt`, `sitemap.xml`, `og-image.png`) from the SPA rewrite;
* serves `sw.js` with `Cache-Control: no-cache, no-store, must-revalidate` so new
  deployments are detected, and the manifest/workbox runtime with `max-age=0`;
* keeps `/api/*` rewritten to Render — the service worker never intercepts or caches it;
* allows the worker under the existing CSP (`worker-src 'self' blob:`).

Installability requires HTTPS (Vercel provides it). After deploying, verify:

```bash
curl -sI https://<your-app>/sw.js | grep -i cache-control      # no-cache
curl -s  https://<your-app>/manifest.webmanifest | head -c 200  # JSON, not HTML
curl -sI https://<your-app>/icons/icon-512.png | grep -i content-type  # image/png
```

Chrome DevTools → Application → Manifest should show no installability errors, and
Lighthouse → "Installable" should pass.

Render needs **no changes** for the PWA: Socket.IO, CORS (`CLIENT_URL` must list the
exact Vercel origin), cookies via the `/api` rewrite, WebSocket upgrade and `/health`
are unchanged.

### Without the rewrite (alternative)

Set `VITE_API_URL=https://<api>.onrender.com/api` and on Render
`COOKIE_SAMESITE=none`. This works in Chromium and Firefox, but browsers that block
third-party cookies (Safari) will drop the refresh cookie, so players must sign in
again after a reload. The rewrite is recommended.

## 3. CI/CD gate

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on every push:
install → lint → typecheck → unit tests → integration tests (real PostgreSQL) →
build, then Playwright end-to-end tests.

* Render deploys only when checks pass (`autoDeployTrigger: checksPass`).
* For Vercel, enable **Settings → Git → "Wait for checks"** (or protect `main`
  with required status checks) so a failing pipeline blocks the production deploy.

## 4. Docker (self-hosting / local full stack)

```bash
cp .env.example .env        # set POSTGRES_PASSWORD, JWT_SECRET, JWT_REFRESH_SECRET
docker compose up --build   # web http://localhost:8080 · api http://localhost:4000
```

* `apps/server/Dockerfile` — multi-stage, production dependencies only, runs
  `prisma migrate deploy` then the bundled server, as the non-root `node` user.
* `apps/web/Dockerfile` — Vite build served by nginx, which also proxies `/api`
  and `/socket.io` to the API (`API_UPSTREAM`).

## 5. Post-deploy checklist

- [ ] `GET /health` → `{"status":"ok"}`, `/health/ready` → ok
- [ ] Landing page loads, `robots.txt` and `sitemap.xml` use your domain
- [ ] Guest sign-in works; reload keeps you signed in (refresh cookie)
- [ ] Two browsers: create room → join by code → play → winner shown on both
- [ ] Refresh mid-game → "Game session restored."
- [ ] Render logs show structured JSON with request ids and no secrets
